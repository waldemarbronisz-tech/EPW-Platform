# Rendering the Synoptic Screen in EPW-OS: Three Paths, Costed

Companion to `SYMBOL_INVENTORY.json`/`.md` (generated by
`generate_symbol_inventory.mjs` - re-run that first if the library has
changed since this was written). This document is reconnaissance only:
**no rendering code was written for this task**, and no decision is
made here - Waldek decides.

Every number below is labeled **ZMIERZONE** (measured directly - a
grep, a line count, an actual import, an actual file read) or
**ZAŁOŻONE** (inferred/assumed - general knowledge about a technology,
or a judgment call not directly tested in this session). Nothing is
stated as fact that wasn't checked one way or the other.

- **85** symbol definitions exist in the registry today (ZMIERZONE -

## 1. What a screen object actually carries (section 2.5's premise)

ZMIERZONE, directly from `studio/synoptic/src/store/types.ts`'s
`SynopticObject` interface and from reading real `.epwsyn` files (this
branch's own `epwsyn_loader.py` work already documents every field):
`id, type, category, x, y, width, height, rotation, scaleX, scaleY,
visible, locked, layer, zIndex?, designation?, name?, deviceId?, tag,
description, color, fill, border, text, font, fontSize, editor?
{preview_state, preview_value, unit, format}, bindings?, tooltip`.

**There is no drawing geometry anywhere in that list.** `type` is a
bare string key - `"water.valve"`, `"scada.boundary_point"` - with no
path data, no shape description, nothing. Every other field is either
placement (x/y/width/height/rotation) or generic styling (color/fill/
border/text/font) that any renderer could apply to *any* shape, not
what the shape actually looks like.

**Answer to 2.5, stated plainly: no, a `.epwsyn` file does not suffice
on its own. A renderer must also know the editor's symbol registry (or
an exported equivalent of it) to know what a `type` string is supposed
to look like, how many states it has, and what each state means
visually.** This is not a close call - the format simply carries no
geometry at all, by design (`DeviceSchema.ts`'s "a screen only says
*at this spot, this symbol, this device*" principle from the epwsyn
loader task applies to the *symbol* half of an object exactly as much
as it applies to the *device* half).

This has a second, sharper edge, ZMIERZONE not assumed: the registry
itself is not a stable contract a file can assume forever - **3 of the
47 types referenced by the four real example files no longer exist in
today's registry at all.** A renderer built against "the current
registry" will still need a graceful "I don't know this symbol"
fallback for old files, not just for symbols added after the renderer
ships (the editor itself already has exactly this fallback -
`GenericSymbol` in `SymbolRenderer.tsx`, a plain rectangle/circle with
the type name as a label, is what any unrecognized `type` renders as
today).

## 2. How the editor actually draws these 85 symbols (background for all three paths)

ZMIERZONE by reading `SymbolRenderer.tsx` and a sample of components:

- Rendering is **`react-konva`** - a `<canvas>`-based scene graph
  (`Group`/`Rect`/`Circle`/`Path`/`Text`/`Line` primitives), not SVG,
  not styled DOM elements.
- Dispatch is **one large hardcoded `switch (obj.type)`** in
  `SymbolRenderer.tsx` (370 lines total including two shared fallback
  components), mapping each `type` string to its own imported
  component. There is no registry-driven/generic dispatch today - the
  switch and the registry are two independently-maintained lists that
  happen to agree.
- The 87 per-symbol component files total **4,860 lines** (ZMIERZONE,
  `wc -l`). Geometry inside them is written *proportionally* to the
  object's own `width`/`height` (e.g. `ValveSymbol.tsx`: `const w =
  obj.width; const h = obj.height;` then every coordinate is a fraction
  of `w`/`h`), not in fixed pixels - relevant to path C below.
- The pure-data registry files (`registry/*.ts`: type/label/category/
  dimensions/states/terminals, no drawing code) total **1,236 lines** -
  cheap to reproduce in any language, since it's just typed data.

### 2a. Which symbols actually animate, vs. which only switch state

ZMIERZONE by grepping for `useState`/`useEffect`/`setInterval`/
`requestAnimationFrame` and reading each hit (two initial grep hits -
`site/HouseSymbol.tsx`, `site/WarehouseSymbol.tsx` - were **false
positives**: `HouseState`/`WarehouseState` type names contain the
substring "useState" by coincidence; verified by reading both files,
neither has any timer or effect at all).

**Exactly 12 of 85 symbols (14%, 638 of 4,860 component lines) run a
real, self-driven, time-based animation**, and there are exactly
**three animation techniques** in the whole codebase, no others found
(no CSS transitions, no Konva `.to()`/`Konva.Animation` tweening, no
spring libraries):

| Technique | Symbols | Count |
|---|---|---|
| Continuous rotation (`requestAnimationFrame` incrementing an angle) | `hvac.fan`, `water.pump` | 2 |
| Blink toggle (`setInterval` flipping a boolean every 500-1000ms) | `electrical.indicator_lamp`, `automation.plc`, `automation.epw_core`, `automation.remote_io`, `automation.epm` | 5 |
| Marching dash-offset (`requestAnimationFrame` incrementing a stroke dash offset, to suggest flow/current) | `electrical.ac_wire`, `electrical.busbar`, `electrical.cable`, `electrical.three_phase_line`, `water.pipe` | 5 |

The remaining **73 symbols (86%) only branch on the discrete `state`
string** (`state === 'CLOSED'` etc. - 102 such comparisons counted
across all 87 files) - no continuous motion, just picking a
color/shape/rotation once per render.

### 2b. Which symbols depend on live wiring, not just their own state

ZMIERZONE from `SymbolRenderer.tsx`'s switch: **23 of 85 symbols (27%)**
receive a `terminalNetState` callback - almost all the water-medium
"aparaty" (`water.valve`/`gate_valve`/`ball_valve`/`drain`/
`solenoid_valve`/`drain_valve`/`pump`/`tank`, and 15 `site.*` water
objects). This callback answers "is THIS terminal currently on an
ACTIVE or INACTIVE net" - not the object's own `state`, but whichever
net(s) its terminals belong to on the *whole diagram*.

That answer comes from `NetResolver.ts` (ZMIERZONE: 328 lines) - a real
graph algorithm: it walks every wire's touching points to group
terminals into nets (a wire ending anywhere along another wire's
length joins its net, not just at endpoints - what makes a busbar tap
work), then marks a net ACTIVE if it touches a source terminal (a
`boundaryDirection: SOURCE` boundary point, or a `SWITCHED` device's
`OUT` terminal currently `CLOSED`). **This is computed fresh from
`connections` + `objects` + `devices` on every render - it is never
stored in the `.epwsyn` file itself.** `water.pump` is both animated
*and* net-dependent (1 symbol in both sets).

**Overlap-corrected split of all 85 symbols:**

| | Count | % |
|---|---|---|
| Neither animated nor net-dependent - pure static "type+state → shape" | 51 | 60% |
| Animated only | 11 | 13% |
| Net-dependent only | 22 | 26% |
| Both | 1 (`water.pump`) | 1% |

### 2c. Runtime's web footprint today

ZMIERZONE: `runtime/requirements.txt` lists no web/browser dependency
at all (`PySide6`, `FastAPI`+`uvicorn`+`SQLAlchemy`+`alembic`,
`paho-mqtt`). ZMIERZONE, in *this* development environment only
(Windows x86-64): `PySide6==6.11.2` already pulls in `PySide6_Addons`
(the sub-package that bundles Qt WebEngine), and `from PySide6 import

resolved by the import succeeding on a Windows dev machine.

## PATH A - Runtime draws every symbol natively in Qt/PySide6

**What has to be ported (ZMIERZONE line counts, ZAŁOŻONE that a line of
Konva JSX costs roughly a line of `QPainter`/`QGraphicsItem` code - not
tested by actually porting one):**

- ~4,860 lines of per-symbol Konva rendering + 370 lines of dispatch
  logic ≈ **5,230 lines** to translate to Qt paint code, for full
  coverage of all 85 symbols. Restricting to the 44 registry-resolvable
  types actually used by the four real projects would be a fraction of
  that (not separately measured - the registry doesn't record
  component line count per symbol, only per-file, and files are not
  1:1 with symbols in every category).
- The 1,236 lines of pure registry data (dimensions/states/labels)
  translate almost mechanically to Python dataclasses/dicts - cheap.
- If net-based coloring is to be preserved for the 23 affected symbols,
  `NetResolver.ts`'s 328-line graph algorithm needs a Python
  reimplementation too - a second, separate porting job, not covered by
  "port each symbol's paint code."
- ~14% of the ported code is animation-specific (three known,
  reproducible techniques - none of them exotic in Qt: `QTimer` +
  `QGraphicsItem::setRotation`, `QTimer` + toggling visibility/opacity,
  `QTimer` + a dash-offset property on a `QPen`).

**What happens when a new symbol is added in the editor:** ZMIERZONE
via the current architecture - nothing on the runtime side notices.
There is no registry the runtime reads today at all (confirmed: no
import of anything under `studio/synoptic/` anywhere in `runtime/`).
Every new editor symbol needs a hand-written Python counterpart added
to a runtime dispatch table, exactly mirroring the manual, unenforced
`switch`/component pairing the editor itself already has - the same
maintenance burden, just duplicated into a second language and a
second team's remit.

**Cost shape:** a large, one-time, then ongoing-per-symbol translation
effort, entirely inside this codebase's normal language/toolchain (no
new runtime dependency, no new process model).

## PATH B - Runtime embeds the real React/Konva renderer in a WebView

**Web dependency today:** none (ZMIERZONE, see 2c above). This would be
the *first* web-technology dependency introduced into EPW-OS.

**Orange Pi implications - ZAŁOŻONE, general knowledge about Qt
WebEngine, not measured on target hardware this session:**

- Qt WebEngine is a full embedded Chromium build. Even an idle,
  content-empty `QWebEngineView` typically costs on the order of
  **150-300+ MB of resident memory** for its own render/GPU/network
  processes, before a single symbol is drawn - this is Chromium's
  known multi-process baseline, not this app's own code. On an Orange
  Pi (1-4 GB RAM class boards, shared with the OS, the rest of EPW-OS,
  and whatever else runs on the device), that is a substantial,
  possibly majority, share of available memory for one screen.
- "Praca miesiącami bez restartu" (the stated deployment requirement)
  is in tension with Chromium's own well-documented behavior under very
  long uptimes (renderer memory growth, periodic internal GC/compositor
  quirks) - mitigated in production browsers by periodic tab/process
  recycling, which is not a pattern this always-on kiosk screen has
  today for anything else it runs.
- Kiosk mode today is a single-process PySide6 window
  (`enter_kiosk_mode()`/fullscreen, confirmed by reading
  `main_window.py` in the epwsyn loader task). Qt WebEngine's
  multi-process Chromium sandbox model is a materially different
  process/crash/restart story than anything else in this app - a
  WebEngine renderer-process crash does not necessarily take the whole
  Qt app down, but recovering it cleanly inside an unattended kiosk is
  new failure-handling surface this app has never needed before.
- Whether a working `PySide6-Addons` wheel with Qt WebEngine even
  installs on the actual target OS/architecture is unverified - if it
  does not, this path is not "harder," it is **not available** on that
  hardware at all until/unless a source build is attempted (itself a
  multi-hour Chromium compile on an SBC-class CPU).

**Live data flow:** TagManager values reaching a symbol inside the
WebView would need a `QWebChannel` bridge (Python object exposed to
JS, or a periodic `runJavaScript()` push) - a new, asynchronous,
serialization-boundary data path that does not exist anywhere else in
this codebase today (every other page reads TagManager directly, in
the same process, no serialization).

**Cost shape:** conceptually the least *rendering* code to write (reuse
the real React app almost as-is), but the largest architectural and
operational risk, concentrated on hardware this was not tested against
in this session.

## PATH C - Editor exports geometry as data; runtime draws generically

This is the path Waldek considers best today. Costed honestly, that
means being explicit about where it works cleanly and where it does
not - not just where it does.

**Where it works cleanly (60% of the registry, ZMIERZONE per section
2b):** 51 of 85 symbols need nothing but a static shape per
`(type, state)` pair - no animation, no live connectivity. Geometry is
already written *proportionally* to `width`/`height` in the source
components (confirmed in `ValveSymbol.tsx` and consistent with every
other file sampled), which is exactly the shape a portable
"normalized path per state" export needs - the object's own `.epwsyn`
`width`/`height` already supplies the scale factor, nothing extra to
carry.

**Where it needs more than static geometry (40%, ZMIERZONE per 2b):**

- **11 symbols (animation-only) and 1 more (`water.pump`, both)** need
  one of exactly 3 known animation *behaviors* attached to a state, not
  just a shape: rotate-continuously, blink-toggle, dash-offset-march.
  This is still boundable - a generic runtime renderer could implement
  these 3 primitives once and let exported data say "state X uses
  primitive rotate at rate Y" - but it is not *pure* static geometry;
  it is geometry **plus a small, fixed vocabulary of animation
  directives** the runtime must also implement natively.
- **22 symbols (net-dependent only) and 1 more (`water.pump`, both) -
  23 total** need to know which of their terminals sit on an ACTIVE
  net *right now*, computed from the whole diagram's wiring - not
  something a per-symbol geometry export can carry, because it isn't a
  property of the symbol at all, it's a property of the diagram. This
  is the one honest crack in the premise: **a geometry export solves
  "what does this symbol look like," not "is this symbol's terminal
  currently live" - that second question requires either (a) porting
  `NetResolver.ts`'s 328-line graph algorithm into the runtime too
  (real logic, not data), or (b) baking a snapshot of resolved net
  states into the exported file at export time, which then goes stale
  the moment wiring changes and would need re-exporting on every edit
  - a live-editing workflow problem, not a one-time cost.**

**Can `SymbolRenderer.tsx` be talked into producing such an export
today?** ZMIERZONE: no exporter of this kind exists. ZAŁOŻONE, based on
reading the code style (proportional geometry, discrete state
branches, no exotic per-pixel logic beyond the 3 animation techniques
above): it looks *feasible* to build one - e.g. a headless script that
renders each `(type, state)` pair through `react-konva`'s own toJSON
capability or a custom Konva-node-to-path serializer - but **this
tooling does not exist and was not attempted or measured in this
task** (GRANICE: zero rendering/export code was written here). This is
a judgment call, not a measurement, and it is exactly the kind of new,
purpose-built export tooling that would need its own scoping.

**How big would such a file be, for the 44 registry-resolvable types
used by the four real examples?** ZAŁOŻONE, not measured (no exporter
exists to run): this inventory's own metadata-only JSON (all 85
symbols, every typed field, no geometry) is **49,182 bytes**
(ZMIERZONE). A real per-state geometry export would be larger - each
state's shape is a handful of primitives (a `Path`/`Rect`/`Circle`
each with a handful of numeric coordinates), so a rough per-state
budget of a few hundred bytes is not unreasonable, putting a
44-type, ~2-3-states-average export in the **tens of KB, not MB** -
but this is an estimate from first principles, not a measured artifact,
and should be treated as such until someone actually builds and runs
the exporter.

**Cost shape:** the best fit for 60% of the library outright, a bounded
(3-primitive) extension for another 13%, and a genuine second
subsystem (net resolution) required for the remaining 27% no matter
which of the three paths is chosen - because that 27% is a property of
NetResolver.ts's algorithm, not of how a symbol happens to be drawn.

## Recommendation

Path C is the right *default* direction, but not a free lunch: it
still requires (1) new export tooling that doesn't exist today, (2) a
small, fixed set of animation primitives implemented natively in the
runtime (3 of them, all straightforward `QTimer`-based effects), and
(3, the real cost center) a Python port of `NetResolver.ts`'s
connectivity algorithm if net-based coloring on water objects is to
render correctly - which is genuinely a second body of logic, not an
extension of "draw a shape." Path A avoids introducing (1) and (2) as
separate concerns (everything becomes hand-written Python either way)
at the cost of ~5,200+ lines of manual translation and zero
future-proofing against new editor symbols. Path B is not recommended
without first empirically verifying Qt WebEngine actually installs and
runs acceptably on the real Orange Pi target - everything else about
it (memory, kiosk-mode risk, months-without-restart) is a real, known
characteristic of Chromium-based embedding, not a solvable unknown.

No implementation was started for any path. This report exists so that
decision can be made with the actual numbers in hand.
